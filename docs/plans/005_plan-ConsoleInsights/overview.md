Authored 2026-10-29 by the planning session (Sonnet 5.5; the execution roster, which does not use Sonnet, is in the model-assignment summary) acting as planner (design decisions reviewed by the `advisor` tool at the first unit, see STATE.md §7). Folder: `docs/plans/005_plan-ConsoleInsights/`.

## Goal and reference scenario

Take pglens from the current branch state (`feat/index-analysis`, HEAD `5929be2` + uncommitted work) to a console that is trustworthy under load, then prove it against a real HA topology.

Reference scenario (the final gate G-FINAL proves all of it on the live Odoo stack):

1. Odoo 18 on PostgreSQL 18 carries seeded data (~30k partners, 3k products, 4k sale orders, 40k messages, 187 modules) and can be restored from `/home/agent/odoo-backups/` onto a throwaway container.
2. `Instance Overview` shows time-axis charts whose x-axis labels are readable (`HH:mm` UTC), **Transactions per second** is a continuous line (>= 95 % non-null buckets) with no balloon markers, the chart region is visually separated from the summary tiles and split into semantic groups (Workload, Memory & I/O, WAL & checkpoints, Queries, Tables & indexes, Host).
3. Host section shows CPU, load, memory, swap and filesystem **charts**; `Filesystem total/free` are populated from the target's `data_directory`.
4. `Index analysis` has four tabs: Indexes, Cleanup, Dead rows, Suggestions. Suggestions are derived from the busiest statements, ranked by weight, with read-benefit upper bound, estimated size and write overhead; a ground-truth workload on a known-unindexed Odoo column is suggested, an indexed column is not.
5. The current Odoo PostgreSQL has been migrated **in place** to an HA topology (1 primary + 2 hot standbys + automatic failover + load balancer, Odoo connected through it), data preserved. pglens shows the three nodes as one cluster, follows a switchover and a hard failover, and every pglens gap found by the drills has been implemented and re-drilled.
6. The monitoring role is raised to Tier 2 at the end with `allow_signal: false` and `commands.enabled: true`.
7. Every data table in the console has a search box and the filters that make sense for its columns, a truthful "Showing X of Y" count, **20 rows per page by default** (selector 20/50/100, D23), and quick ascending/descending sort buttons on every sortable column; state survives a reload through the URL.
8. A cluster (and an instance) can be renamed from Settings; the new name appears everywhere it is shown, survives page reloads, agent restarts and inventory refreshes, and an empty name reverts to the default label.
9. Settings is a tabbed control surface instead of a read-only inventory: Inventory, Preferences (theme, default time range, refresh interval), Data retention (per data family, with a dry-run preview and a confirmation before shortening), Advisor rules (enable/disable), Notifications (channel status, write-only secrets, test send), Names (clusters and instances), Audit & server. Everything that cannot be configured from the UI is listed with its reason in `settings-inventory.md` (11.0).
10. For every monitored server the console says when something that is not configured prevents FULL monitoring: a per-instance "Monitoring readiness" view (banner on every instance page, fleet badge, dedicated section) lists each warning with the features it costs and exact enabling instructions — through the console where a console control exists, otherwise copy-ready SQL / PostgreSQL configuration / `agent.yaml` / host-mount steps (D25).
11. The console is optimised for a Full HD monitor: at 1920×1080 and at 1920×950 (maximised browser) every table page shows its default 20-row table, toolbar and pager without a page scrollbar and without a horizontal scrollbar (D26).
12. ASH / wait analysis shows one chart per wait group (CPU, I/O, locks and contention, client and inter-process, other) with its own scale and a clear legend, instead of a single crowded stacked chart (D24).
13. Locks and activity make the origin of every session explicit: sessions opened by pglens itself and sessions opened by the application are counted and listed separately (two tables), and the connection tiles show the split (D27).
14. Active sessions carry full connection and active-query information (client, ages, wait, query id, normalised or opt-in raw text, blocking relations, connection summary by origin/application/user/client/database/state), and per-application connection counts are on by default (D28).
15. Front-end tests use Playwright against the live stack (real browser, real Odoo load): the stack may be stopped, rebuilt and brought up again, Odoo and PostgreSQL are stimulated with known workloads, and every pglens indicator is checked three ways (UI, pglens API, PostgreSQL ground truth) — [test-strategy.md](test-strategy.md) is the authoritative strategy (D29).
16. Every chart, tile, table, section and settings control carries a plain-language caption stating exactly what it shows or monitors, the unit, window and source, and how to read it; technical terms are glossed, and a small circled ⓘ on each card opens a hover tooltip with the extra detail (D30).
17. Summary cards are unambiguous: one primary figure with a real unit, any further number only inside a labelled sentence ("9 redundant prefix indexes"), never an unlabelled second figure (D31).

Exclusions: no `git push` and no branch creation/switch; local commits follow D11 (user-set `full-autonomous` + WIP commits); no network access beyond the local network except what the user authorized (image pulls/builds for the existing Odoo stack; HTTPS POST to the user-provided Google Chat dev webhook host; Patroni/etcd/HAProxy images are not authorised, D9); no new third-party Go/JS dependency (hand-written heuristic SQL extractor); no change to existing check semantics except the explicit default change of D28 (recorded in STATE §8).
