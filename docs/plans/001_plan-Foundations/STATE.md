## 2. Feature context (self-contained recap)

Build the verified foundations of `pglens`, a self-hostable PostgreSQL fleet
monitor: an agent that scrapes real instances through a version- and
permission-aware check registry, a server that ingests a versioned JSON envelope
into TimescaleDB with correct counter-to-rate conversion and reset detection, and
an L1/L2/L3 test harness that proves the chain stays correct under real failures.
No frontend in this plan — the HTTP API is the contract. The value delivered is
correctness later work can build on, not feature breadth.

**Reference scenario:** with a `primary-standby` stack running, `make scenario
ID=SYS-REPL-001` promotes the standby; afterwards `GET /api/v1/clusters` reports
the roles inverted, exactly one `failover_detected` event exists, and the
`cluster_id` is byte-identical to the value observed before the promote. Must
pass with `AGENT_MODE=container` and `AGENT_MODE=binary`.

**Hard constraints:** PostgreSQL 15–18 only · no `CREATE EXTENSION` required on
monitored instances · the whole check suite must run at permission tier T0 · the
agent must never exceed its connection budget, never block on a lock, never crash
and never fill the host disk · every gate green with `-race`.

**Key decisions in force:**
D8 module `github.com/manprint/pglens` · D9 `tenant_id` present, single-tenant
behavior · D10 hybrid TSDB schema: typed hypertables for statements, ash,
replication + one generic · D11 PostgreSQL 15–18 · D12 JSON wire with versioned
envelope · D13 bootstrap token plus working revocation, no rotation or mTLS ·
D14 no frontend, test levels L1/L2/L3 only · D15 minimal ASH in scope (phase 7) ·
D16 per-database level in scope · D17 deltas computed server-side · D18
`cluster_id` on the wire is a JSON **string** · D19 buffer 6h < sample age 12h <
compress after 48h · D21 `cluster_id` stored as `bigint` bit pattern · D22
connection budget 3, then 4 from phase 7.

- **V001-F12 (MINOR, OPEN, new this session)** — `internal/agent/buffer.Buffer` cannot ever reclaim disk space for a buffer smaller than its own hardcoded 8 MiB segment-roll threshold: `enforceMaxSize`/`enforceMaxAge` (the only code that ever deletes a segment) require a SECOND segment to already exist before they can delete the first, but a buffer configured (or physically capped, e.g. by a small tmpfs) below 8 MiB can never roll to a second segment in the first place — so once it hits real ENOSPC, `Append()`'s `BufferFull` latch (set by `handleWriteError`, checked at the very top of `Append()`) becomes **permanent**: every future `Append()` short-circuits before ever reaching the write that would clear it, so the buffer can never accept another envelope until the agent process itself restarts, no matter how long afterward the backlog would otherwise have room to drain. Found live via `SYS-AGENT-003` (a 16 KiB tmpfs): `buffer_stats.acked` froze at a fixed count the instant ENOSPC first hit and stayed frozen for a full 10-minute live observation window while `dropped` climbed monotonically forever — not a timing issue, a structural one. Not fixed this session (a real behavior-changing fix to `buffer.go`'s segment sizing, not a quick patch) — `SYS-AGENT-003`'s own scenario was corrected instead to match `phase_06.md`'s actual literal wording (dropped grows, no crash, PG unaffected — it never actually asked for bounded-time recovery). Worth fixing eventually: segment-roll size should probably scale with (or be capped by) the configured buffer size, not be a fixed 8 MiB regardless of it.

## 10. Do-not-repeat

- Do not add load-based adaptive sampling to the scheduler. `IDEA.md` v0.1
  proposed it; it removes resolution exactly during an incident. Rejected in
  sub-phase 4.2 with the reasoning written into the phase file.
- Do not reintroduce `Query()` alongside `Scrape()` on the `Check` interface.
  The v0.1 draft had both; `Scrape` covers everything.
- Do not represent `cluster_id` as a JSON number (D18) or as PostgreSQL
  `numeric`/`text` (D21). Both were considered and rejected for stated reasons.
- Do not route ASH bucket counts through the delta engine. They are independent
  per-window observations, not counters (sub-phase 7.3).
- Do not build a test-only copy of `deploy/sql/monitoring_user.sql`. The L2
  harness applies the shipped file so the script users run is the script tested.
